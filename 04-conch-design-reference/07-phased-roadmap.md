# 三仓联合实施路线

> 每阶段交付一个可验证的用户流程，三个仓可同时修改；PR 按仓提交，commit 按逻辑拆分。

## 阶段 0：确认基线与架构

**输入：** 用户需求、[上游能力](01-current-system-boundary.md)、[候选决策](02-adopt-adapt-reject.md)。

Conch 核对 Template/BootPreparer/恢复与授权，StratoVirt 核对设备/UFFD/运行控制，lazyd 核对数据源/缓存/并发。查询最新 upstream，记录 commit；增量恢复依赖以实际合入版本为准。

**交付：** 架构图、资源类型、正常/失败时序、候选对照和验证门槛。先给维护者审阅架构，再进入产品代码。此阶段不冻结无实验依据的全部 ABI。

StratoVirt 另列最小改动清单：每项说明现有 helper/backend 为何不足、必须在 VMM 执行的动作及回归范围。内容索引、下载、预取和 GC 留在 Conch/数据源，不把统一 UFFD/迁移框架列为前置；边界见[分仓职责](05-stratovirt-responsibilities.md)。

## 阶段 1：最小端到端选型实验

| Conch | StratoVirt | lazyd/临时数据源 |
| --- | --- | --- |
| 生成最小资源计划，记录启动和失败 | 先验证外部 UFFD 接入、只读映射和失败路径；内部 handler 仅在必要时补原型对照 | 提供固定内容、延迟、错误、共享缓存及已有块后端样例 |

实验覆盖 pmem 与整盘块方案的关键区别；块方案复用已有设备/外部后端，缺少接入时先记录限制，不额外开发 VMM NBD/COW 引擎。用本地 mock 和真实 KVM/guest 验证地址、写保护、取消和唤醒；将结果反馈到决策文档。

**退出条件：** 选定首条数据路径、handler 位置和必要能力协商；不可行的方案有可复现原因。新增 pmem 产品路径只保留一种 handler/页完成组合，不扩写未选候选。实验不混入产品路径。

## 阶段 2：冷启动最小产品闭环

| Conch | StratoVirt | lazyd |
| --- | --- | --- |
| 选择性准备、持久资源引用、启动 source、guestd 设备/挂载 | 复用 backend/区域，补所选接入与页完成、只读保护、就绪/错误/关闭 | 持久缓存、校验/授权、供数和运行 attachment |

首版包含完整错误策略、引用保护与普通路径回归，不用“以后补生命周期”解释当前阻塞或误删风险。

**验收：** 不完整下载目标镜像即交付业务；与完整路径对拍；失败可取消；两 VM 共享内容；删除不影响其他使用者。

## 阶段 3：Checkpoint 恢复闭环

复用最新合入的磁盘/内存恢复能力。Conch 组织一致视图与恢复屏障，StratoVirt 处理 RAM/设备恢复和代次，lazyd 或已有专用后端支持需要的不可变数据来源。

远端化主要接入数据来源：VMM 保留已有恢复、dirty tracking 和设备状态路径，只补实际缺失的生命周期接口。父层内容索引不移入 StratoVirt，也不要求先统一 pmem/RAM 协议。

**验收：** 冷远端恢复、父层索引、私有写入、晚到填充、二次 checkpoint、跨节点重绑定、发布失败与回收。架构从阶段 0 考虑这些需求，实现允许分阶段。

## 阶段 4：性能策略和规模

Conch 提供场景/预算，数据服务利用 handler 事件和已有指标执行工作集预取与有界窗口；只有证明确需额外反馈时才增加最小 VMM 接口。若选择文件映射，缓存范围提前映射由数据源提出、VMM 在合法范围内执行，不在 VMM 内实现网络预取策略。

比较 full、纯按需、预取和提前映射；测业务可用时间、首请求、p50/p99、下载放大、PSS、资源泄漏与恢复最终完成时间。覆盖小镜像、高层数、随机访问、冷/热缓存及隔离网络模拟。

**独立可选实验：** [远端聚合启动工作集](../03-design-comparison/06-cache-dedup-and-prefetch.md#远端聚合启动工作集)。先用只读镜像和授权样本验证“需求采集 → 异步聚合 → 版本化清单 → 本地有界预取 → 效果反馈”；不作为阶段 2/3 前置，不新增 StratoVirt 热点学习框架，也不预先要求独立统计服务。

与纯按需、静态工作集分别对照，使用未参与学习的启动样本并区分冷/热及采样条件。检查需求与预取计数分离、内容版本绑定、租户隔离、采集成本和下载放大；统计服务不可用或清单无效时必须继续普通按需启动。算法、API 和默认阈值在验证后再定。

只有测量证明收益后才选择默认策略。

## 如何组织 PR 和 commit

每仓可以一个完整功能 PR，三仓同时开发和评审；跨仓协议变更必须对应测试和版本协商。合入/发布顺序根据最终依赖决定，不写死“先 lazyd、最后 Conch”。

建议按以下逻辑组织各仓 commits，不要求数量固定：

| 仓库 | commit 边界 |
| --- | --- |
| Conch | 资源契约与配置；选择性准备/发布；VMM/guestd 接入；生命周期与恢复；场景测试 |
| StratoVirt | 必要配置与区域接入；所选 handler 的最小交互；映射/填页校验与完成；就绪/失败/关闭；边界回归测试 |
| lazyd | 内容身份与完整性；缓存持久化；调度；类型适配；attachment/授权；恢复与协议测试 |

共享协议测试随字段改动提交，不能所有测试留到最后。无关清理不混入功能；修复折回负责该逻辑的 commit，保持每项改动可解释。

## 发布门槛

- 三仓版本组合明确，能力不足时在启动前失败或使用用户明确允许的完整策略。
- 正常启动、已有快照、关闭与安全要求通过回归。
- 新路径真实端到端通过；mock 只证明接口，不代替 guest 验证。
- 已知风险、未覆盖架构/内核及性能条件写清。
- 本文是执行路线，本次文档重写没有完成上述实验。
