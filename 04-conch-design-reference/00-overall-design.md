# Conch + lazyd + StratoVirt 懒加载整体设计

> 只读这一篇，就能理解我们的目标、三仓分工、一次启动怎样完成，以及共享、失败和快照怎样处理。正文只讲方案，研究依据与实现细节放在文末。

**本文是目标设计，不是已完成功能清单。** 当前主线明确为只读 EROFS + pmem/DAX；外部 UFFD 接入、文件映射完成方式和跨仓接口仍需实验确认。

## 1. 我们要实现什么

用户通过 Conch 创建沙箱时，不必先下载全部 rootfs 内容。启动必需的资产先准备好，文件数据在实际访问时由 lazyd 按需供应；多台 VM 使用同一内容时，尽量共用下载、磁盘缓存和干净文件页。

目标是**更早交付业务可用的沙箱，同时保证内容正确、写入隔离、失败可处理、资源可回收**，而不只是让 pull 或 VM 启动命令提前返回。

| 数据 | 设计方式 | 交付范围 |
| --- | --- | --- |
| 只读镜像文件 | 原生 EROFS 通过 virtio-pmem 暴露给 guest，使用 DAX 访问，缺失内容按需补齐 | 首版主线 |
| kernel、initrd 和关键配置/索引 | 启动需要的内容先完整准备 | 首版必需 |
| 运行时新增、修改的文件 | 写入每个沙箱独立的可写层，不修改共享 EROFS | 首版保持写入隔离；历史写层的远端懒加载后续接入 |
| Guest RAM 快照 | 复用 VMM 恢复能力，后续增加远端按需来源 | 从架构上考虑，分阶段实现 |

这里的 EROFS 是只读文件系统；virtio-pmem 为 guest 提供可映射的数据区域；DAX 让 guest 绕过文件数据页缓存访问该区域。它仍可以使用宿主机文件缓存，不等于把这部分内容变成 guest 的普通可写 RAM。

普通完整启动路径保留。首版不增加 fanotify 作为 guest pmem 触发入口，也不并行实现另一套整盘懒加载方案。

## 2. 整体架构与分工

可以用三句话记住分工：**Conch 组织一次操作；lazyd 找到并供应正确数据；StratoVirt 让虚机安全地访问这些数据。**

| 组件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Conch，宿主机侧 | 解析镜像/快照、组织资源与授权、选择完整或按需准备、管理启动/恢复/失败/删除 | 不参与每次缺页取数，不亲自改写 VMM 地址空间 |
| lazyd，宿主机侧 | 访问远端、管理共享缓存与取数任务、控制资源用量、处理会话权限和缓存回收；按选定路径接缺页适配器 | 不管理 vCPU、guest 挂载或 CPU/设备快照状态 |
| StratoVirt，宿主机侧 VMM | 创建虚机设备和内存区域，交接或处理缺页，校验并执行必要的映射/填页，报告就绪和致命失败 | 不解析 OCI、下载镜像、执行预取算法或回收内容缓存 |
| guestd，虚机内 | 识别设备、按正确顺序挂载 EROFS 与可写层，组装业务 rootfs | 不访问 registry，不管理宿主机缓存 |

guestd 属于 Conch 仓库，不是第四个独立产品。lazyd 内部的适配器、调度和缓存也是逻辑模块，不意味着每项都新增进程。

**控制流程与读数据流程分开。** Conch 建立资源关系、等待就绪并处理最终结果；运行后，缺页主要在内核、handler、lazyd 和 StratoVirt 之间完成，Conch 不作为每次读取的中转站。

## 3. 先分清数据、来源和使用者

| 对象 | 回答的问题 | 谁管理 |
| --- | --- | --- |
| 内容对象 | 究竟是哪份不可变字节，格式与大小是什么，哪些范围已可读 | lazyd 管本地内容与缓存；Conch 保存持久内容引用 |
| 数据来源 | 从哪里取得这些字节，用什么授权访问 | Conch 提供授权引用，lazyd 执行访问和凭据刷新 |
| 运行会话，或 attachment | 哪台 VM 正在使用哪些内容，具有什么权限，何时取消或释放 | Conch 建立/释放，lazyd 与 VMM 管各自的运行状态 |
| 共享取数任务 | 哪段内容正在下载，谁在等待，任务是否成功 | lazyd 在内容级管理 |
| 快照视图 | 逻辑页/块最终来自哪个历史层，哪些是继承或显式零 | Conch 固定依赖关系，数据源适配器解析具体来源 |

例如 VM1 和 VM2 使用同一镜像层：它们有两个会话，但在允许共享的安全域内指向同一内容对象。刷新 VM1 的凭据或重复 prepare，不应重建这个对象，也不应让已有下载任务失去去重关系。

内容摘要是身份依据，不是授权凭证。缓存命中也要验证访问权限；本地缓存路径、socket 和 FD 数字只在当前节点/进程中有意义，不能作为跨节点持久身份。

lazyd 围绕这些对象划分内容核心、来源访问、会话管理、pmem 适配器和有界调度。先确定状态归属，再决定哪些现有代码保留或重组，不提前要求通用插件框架。

## 4. 一台沙箱怎样启动并读取文件

下面按**优先验证的外部 UFFD + 文件映射方向**说明完整流程。UFFD 是 Linux 的用户态缺页处理机制；handler 是读取事件并组织处理的程序逻辑，当前建议放入 lazyd 的 pmem 适配模块。最终位置与完成协议由首轮实验确认，首版只落地一组新增 pmem 路径。

### 4.1 准备：知道要读什么，不先取回全部文件

1. Conch 解析镜像元数据，确定 rootfs 内容、层顺序以及 kernel/initrd 等启动资产。
2. Conch 完整准备必需资产，把明确的只读内容描述和授权交给 lazyd；按需 rootfs 不走完整 payload 下载。
3. lazyd 校验身份、格式和大小，打开或创建共享缓存，确认可以按需读取，返回准备结果。
4. Conch 只有在整组资源准备成功后才发布可用记录；失败则清理本次临时使用关系。

建议先使用稀疏缓存文件（sparse）存数据、位图（bitmap）记录可用范围。稀疏文件可以先声明完整逻辑长度，再逐段写入；逻辑大小并不代表已下载量。bitmap 记录哪些范围达到服务承诺的 ready 条件。**prepare 成功表示能按需供数，不表示完整下载或 unpack 完成。**

### 4.2 启动：先具备处理访问的能力

1. Conch 为本次运行建立独立会话，绑定内容、设备布局、权限和预算，再启动 StratoVirt。
2. StratoVirt 预留 pmem 的宿主机虚拟地址区域，并通过 KVM memory slot 关联 guest 物理地址。下文简称这两种地址为 HVA 和 GPA。
3. 对尚未填充的区域注册 UFFD MISSING。文件映射方向使用匿名/预留区域，不把未下载的 sparse 文件整体 mmap 成完整 pmem 后端。
4. 外部 handler 方向由 StratoVirt 交接 UFFD FD 和区域布局；lazyd 登记会话/区域代次，准备接收事件，双方确认就绪与失败通道。
5. 只有相关缺页能够被处理后，才允许 guest 或设备恢复代码访问该区域。
6. guestd 在 guest 内按稳定设备身份匹配各层，使用只读 EROFS + DAX，并按层顺序与私有可写层组装 rootfs。

FD 即文件描述符，是进程访问文件或内核对象的句柄。这里有两种：**UFFD FD 用于缺页事件与处理；缓存文件 FD 用于访问文件数据。** FD 可通过 Unix 域套接字的 SCM_RIGHTS 机制传递，但发送成功不等于对方已准备好处理请求。

### 4.3 首次读取：补数据，再完成访问

以 guest 首次读取一个尚未加载的库文件为例：

1. DAX 将文件读取落实到 pmem 区域的内存访问；对应 HVA 页缺失时，宿主机内核产生 UFFD 事件，当前访问等待。
2. handler 校验事件属于哪个有效区域，计算区域内偏移；pmem 适配器再定位到确定内容的范围。
3. lazyd 命中 ready 缓存就直接使用；已有取数任务就等待其结果；否则登记任务并按授权读取远端缺失范围。
4. lazyd 检查响应位置、长度及所需完整性条件，写入缓存，完成持久化后发布 ready。
5. lazyd 将只读缓存文件 FD 和就绪范围交给 StratoVirt。后者校验文件、偏移、范围、权限和区域代次，在自己的 HVA 中执行文件映射替换。
6. 完成相应 UFFD 等待，guest 重试并读到正确字节。

`mmap(MAP_FIXED)` 表示替换指定地址区间的映射，必须由拥有该地址空间的 StratoVirt 执行或严格控制。外部 handler 不能直接用自己的普通 mmap 修改 VMM 的 HVA。MAP_PRIVATE/MAP_SHARED 标志、wake 顺序及重复事件处理需通过真实 KVM 测试确定。

文件 FD 可以覆盖大于本次需求的范围，但只允许映射已经确认 ready 的合法区间。最后一页中真实 blob 之外的尾部字节和设备对齐 padding 按定义补零；**尚未下载的真实数据绝不能当零返回。** 缓存记录单元、下载窗口、映射范围分别定义，不统一写死为某个页大小或 1MiB/2MiB。

### 4.4 第二台 VM：共用数据，各自完成映射

VM2 读取同一范围时，若 VM1 正在下载，加入同一任务；若数据已 ready，跳过远端读取。两个 VMM 仍分别检查自己的事件并建立映射，不会因为 VM1 下载成功就自动更新 VM2 的页表。

当它们映射同一实际缓存文件的相同干净页时，可以共享宿主机物理文件页；相同内容存成两个独立文件则不能仅凭摘要相同获得这种共享。收益需要分别测下载量、磁盘占用和 PSS，而不是把两台 VM 的 RSS 相加就判断共享失败。

## 5. 正确性、失败和回收怎样保证

### 数据可读与请求结束分开判断

持久缓存按以下顺序发布：

**完整写入并检查 → 缓存数据同步 → bitmap ready 写入并同步 → 通知等待者。**

下载中、写到一半或同步失败，都不能宣告 ready。失败也要通知等待者，因此收到通知后必须检查结果。只检查文件存在或 sparse 洞不足以证明内容正确；整 blob 摘要也不能直接验证任意小范围，局部强校验需要可信分块摘要等依据。

### 服务有上限，失败有终点

lazyd 对连接、队列、下载并发、缓冲字节和阻塞磁盘工作设置上限。socket 等待不能阻塞异步服务线程，网络操作不长期占住状态锁；超额请求背压或明确拒绝，不无限加线程或堆内存。

当前缺页优先于后台预取，同时限制单会话占用。请求有截止时间，重试有预算；准备失败阻止启动，运行中的不可恢复供数失败必须报告给 VMM/Conch，使受影响 VM 进入明确失败或停止状态，不能只记录日志后永久阻塞。

VM1 取消只撤销它的等待。VM2 仍需要的共享任务继续；已无等待者的任务按预算取消或完成，不能无期限保留。旧区域、旧会话的晚到结果不得安装到新的地址区域。

### 共享文件不能被写坏或误删

lazyd 内部写缓存句柄与外发只读句柄分开；VMM 校验 host 映射及 guest 写保护，不能只依赖 guest 的只读挂载选项。FD 通常授予整个文件的访问能力，授权范围必须与实际导出对象匹配。

关闭按以下责任收尾：Conch 发起停止/取消；各组件禁止本会话新请求，结束或撤销在途操作；StratoVirt 解除相关映射/句柄；lazyd 再释放本会话的保护关系。**删除一个沙箱，不等于删除共享内容。**

缓存回收还要检查其他会话、运行映射、在途任务及重启后的使用关系。断开 socket、关闭服务端 FD 或租约过期都不能撤销 VMM 已有映射；容量不足时不能截断仍受保护的文件。发现已映射缓存损坏，应隔离对象并报告受影响会话，不能只清 bitmap 后原地重写。

可重新获取的本地缓存与快照唯一持久来源分别管理：缓存满足释放条件后可以淘汰，但仍被快照引用的必要来源不能随缓存 GC 删除。

## 6. 后续扩展与实施顺序

### 快照：统一资源关系，保留各自恢复规则

Conch 保存的 checkpoint 是一个一致资源集合：只读镜像引用、磁盘历史层、RAM 来源、CPU/设备状态，以及布局和兼容要求。保存时协调执行与 I/O，固定同一快照代次，持久化必要内容或可靠引用后再发布；失败不破坏旧 checkpoint。

恢复时先确定依赖关系与授权，并行准备所需来源、新私有写层和索引，再按真实访问时机恢复设备与 CPU 状态。不能只在 vCPU resume 前检查，因为设备恢复也可能提前读内存。

| 路径 | 可共享什么 | 必须独立管理什么 |
| --- | --- | --- |
| 只读 pmem 镜像 | 不可变内容、取数任务和干净文件页 | 每个 VM 的设备、映射和等待状态 |
| 磁盘历史层 | 已封存的不可变块及其取数缓存 | 当前写层、覆盖顺序和封存状态 |
| RAM 快照来源 | 不可变快照字节及其下载缓存 | 每个 VM 的填页、写入、脏页与恢复代次 |

lazyd 可用不同适配器复用内容核心，也可接已有专用后端；不把当前可写磁盘或 RAM 脏页塞进共享镜像 bitmap。继承父层、显式零和远端尚未下载分别处理；迟到的 RAM 填充不能覆盖恢复后的新写入。

完整内存快照已在本地时，按需驻留只能延后本地页加载。后续远端懒加载要减少的是此前的完整下载，两者不能混为一谈；复用 VMM 的恢复机制，不要求先统一 pmem/RAM 协议或重写迁移框架。

### 性能：先可靠按需，再加有界预取

Conch 提供启动/恢复场景与预算，lazyd 根据需求和缓存状态执行请求合并、工作集预取或动态窗口。提前映射本地 ready 数据与提前下载远端数据分开测，后台任务不能挤死前台缺页。

远端聚合多个启动样本、生成热点范围清单属于可选增强。清单绑定内容版本、受授权与预算约束；不可用时继续普通按需。跨用户统计默认关闭，也不要求 StratoVirt 增加热点学习系统。

### 分阶段交付

1. **确认架构与关键机制。** 固定各仓实际开发基线，先审阅架构，再用最小实验确认外部 UFFD、只读映射、完成与失败边界；仅在必要时对照内部方式，最终只选一条新增 pmem 路径。
2. **完成冷启动闭环。** 三仓共同接通选择性准备、稳定设备挂载、共享任务、有界 I/O、持久化、权限与关闭。失败处理和引用保护属于首版，不后补。
3. **完成快照恢复。** 基于实际可用的恢复接口接磁盘/RAM 远端来源，验证父层、显式零、私有写入、跨节点绑定和二次 checkpoint。
4. **验证性能策略与规模。** 再比较预取、动态窗口、提前映射和可选批量同步，覆盖冷/热缓存、不同网络及多 VM 负载。

每个阶段同时推进相关三仓工作，按实际依赖组织发布。验收看文件/内存对拍、业务可用时间、首请求与尾延迟、下载放大、共享收益和失败后的资源状态；mock 不能代替真实 guest 验证。

**仍需确认：** handler 的最终位置、文件映射标志与完成顺序、区域/布局契约、会话保护及重启协调的具体接口、局部校验信任边界。本文确定职责和正确性要求，不提前冻结 CLI、JSON 字段或进程数。
