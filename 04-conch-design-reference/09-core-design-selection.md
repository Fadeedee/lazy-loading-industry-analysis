# 核心设计选型与验证计划

> 比较缓存组织、持久发布、共享任务和缺页处理方案，明确三仓改动与验证步骤。

**状态：外部 handler 为主方案方向，关键实验尚未执行。** lazyd 作为独立服务，Conch 为调用方之一，StratoVirt 改动收敛。缓存格式、持久提交、任务模型与数据面 ABI 仍待选型；通用服务边界见[lazyd 设计](../06-lazyd-design/README.md)。

## 1. 先固定什么，不固定什么

| 类别 | 当前立场 |
| --- | --- |
| 产品范围 | 三仓共同修改；只读 EROFS + pmem/DAX 是本轮范围，可写层隔离；架构考虑后续快照远端来源 |
| 正确性 | 缺失不冒充零、读取有权限、新写入隔离、持久发布可恢复、失败可结束、共享资源不误删 |
| 工程边界 | Conch 管资源操作；lazyd 负责内容供应；StratoVirt 只补必要虚拟化能力，复用最终上游恢复接口 |
| 未定实现 | 单文件还是 chunk 文件、ready 的表示、提交与同步策略、任务模型细节、handler 交接和完成协议 |
| 不是前置 | 保留旧 API、旧 Instance、旧 bitmap header、旧 commit 栈；为选型实现全部候选产品路径 |

pmem 范围不等于所有机制已经选定，也不承诺 pmem 比所有块设备方案更快。如果出现 guest 支持、设备规模或恢复一致性的硬阻碍，再单独提出范围变更，不悄悄增加另一条首版主线。

**选型标准：** 各候选使用相同的正确性门槛和性能条件，综合比较实现、迁移与维护成本。

## 3. 外部实现具体给了什么启发

### 3.1 Nydus：内容布局与任务状态是两层问题

[Nydus 镜像设计](https://github.com/dragonflyoss/nydus/blob/8aa80aee6e77a0c4d529581fc6339e9ff3066736/docs/nydus-design.md)描述 bootstrap、blob 与 chunk 信息的关系，chunk 元数据可包含位置和摘要。文档的格式细节主要针对 RAFS v5，不能直接当作 v6/v3 或原生 EROFS 的全部布局。[SRC-NYDUS-001]

[状态接口](https://github.com/dragonflyoss/nydus/blob/8aa80aee6e77a0c4d529581fc6339e9ff3066736/storage/src/cache/state/mod.rs)和 [BlobStateMap](https://github.com/dragonflyoss/nydus/blob/8aa80aee6e77a0c4d529581fc6339e9ff3066736/storage/src/cache/state/blob_state_map.rs)将 ready 查询和 pending/等待协调分开。等待者被通知后还要检查结果；结束 pending 不等于读取成功。[SRC-NYDUS-009] [SRC-NYDUS-010]

**可以借鉴：** 明确内容定位、局部校验依据、任务与 ready 的边界。**不能推出：** 必须用我们的单 sparse 文件、同样的位图粒度，或对方已解决我们所需的取消、掉电和授权隔离。

缓存布局怎么选，仍需下文 S1/S2 对照。Nydus 使用 chunk 概念不代表“每个 chunk 一个缓存文件”。

### 3.2 SOCI：索引解决“去哪里取”，不是“本地是否 ready”

[SOCI 固定版本术语](https://github.com/awslabs/soci-snapshotter/blob/238af848f32fcb887072c144b09ee65a3a895f9c/docs/glossary.md)将 zTOC 分为解压后 TAR 的文件位置表和压缩引擎检查点，span 是能够独立解压的范围。[SRC-SOCI-004]

**可以借鉴：** 将定位索引与本地缓存状态区分，比较取数粒度对下载放大的影响。**不能照搬：** 原生 EROFS 不需要为定位文件再复制一套 TAR/gzip zTOC；SOCI 的 span 大小也不能直接成为 bitmap 单元或主机页大小。

若增加可信分块摘要，需将完整性信息绑定到确定的 EROFS blob，并评估生成、分发、授权和格式兼容对 Conch/lazyd 的影响。

### 3.3 E2B：使用关系关闭，不代表所有缓存都可删除

[E2B NBDProvider](https://github.com/e2b-dev/infra/blob/cc7c574233ad98665a7c72a3d37b0af89ae79a71/packages/orchestrator/pkg/sandbox/rootfs/nbd.go)区分设备准备结果、路径等待和关闭；关闭涉及 flush、mount、overlay 以及错误收集。[SRC-E2B-004]

**可以借鉴：** ready、进行中操作和最终释放必须区分。**差异：** 对方这里管理的私有可写 cache，不是跨 VM 共享的不可变 EROFS 缓存。我们必须另外验证导出 FD 与映射的保护。

### 3.4 外部 UFFD 与 COPY/remap：职责与完成方式

[Nydus UFFD 服务](https://github.com/dragonflyoss/nydus/blob/8aa80aee6e77a0c4d529581fc6339e9ff3066736/service/src/block_uffd.rs)和[完成协议](https://github.com/dragonflyoss/nydus/blob/8aa80aee6e77a0c4d529581fc6339e9ff3066736/service/src/uffd_proto.rs)提供事件交接和文件范围完成的参考；[Firecracker 外部 handler](https://github.com/firecracker-microvm/firecracker/blob/7699746649826d1dfcdde626b3131bac08f28e0d/docs/snapshotting/handling-page-faults-on-snapshot-resume.md)提供 RAM 的 COPY 对照。[SRC-NYDUS-005] [SRC-NYDUS-006] [SRC-FC-002]

**可以借鉴：** 谁消费事件、谁拥有地址空间、如何完成与失败。**不能推出：** 外部 handler 一定改动少，或 RAM 的 COPY 状态机可直接替代只读 pmem 设计。对比按新增状态、往返、关闭和回归成本进行，而不是按“已有 helper”直接定案。

更长的产品解释保留在[数据服务比较](../03-design-comparison/08-data-service-architecture.md)，这里不复制全部调研。

## 4. 选型一：缓存字节怎么存

### 候选与成本

| 候选 | 字节组织与映射 | 可能的收益 | 必须测的代价 |
| --- | --- | --- | --- |
| S1：每内容一个 sparse 文件 | 逻辑 offset 保持稳定；另有 ready 索引；映射同一文件的 ready 范围 | 文件数少，连续映射容易表达 | 子范围回收、活跃映射保护、损坏隔离和 ready 恢复复杂度 |
| S2：不可变 chunk 文件 | 内容范围索引指向独立、对齐的 chunk 文件；VMM 分别映射各文件范围 | 提交/保护/淘汰可细到文件对象 | inode/目录/FD 数、VMA 数、碎片、索引和发送多个文件的开销 |
| S3：chunk 存储加映射视图 | 底层分块，上层重建连续可映射视图 | 可能同时获得块管理和连续布局 | 若重建靠复制，会重复磁盘/page cache；视图另有寿命和恢复协议 |

S1 可复用现有实现建立基线，S2 需要分块与索引原型。S3 暂只做成本审查；若 S1/S2 均无法满足要求，再开展原型验证。

### 会改变三仓什么

- Conch：持续引用确定内容和逻辑布局，不把文件数、FD 数量或缓存路径固化成持久身份。
- lazyd：实现内容 offset 到具体缓存对象的定位，管理文件保护、提交和回收。S2 需要可靠索引；跨 blob 的 chunk 去重还需要可信内容身份，不能凭相同 offset 共享。
- StratoVirt：接收经过授权的文件范围，检查目标/源偏移并完成映射。不解析 chunk digest 或目录布局；但 S2 的多 FD、多 VMA 和完成批次成本会影响最小接口。

**决定条件：** 先排除内容错误、资源无界或关闭不能结束的候选，再比较实际工作集下的文件/VMA/FD 成本、共享收益、缓存淘汰和恢复成本。不能只因 S1 代码已经存在就省略比较。

## 5. 选型二：可读性、持久化和完整性怎么表示

存储布局和 ready 表示有关，但不是同一个选择。bitmap、区间索引、已提交对象清单都可能表达可用范围；必须说明恢复时如何可信地重建状态。

| 候选 | 发布顺序 | 限制 |
| --- | --- | --- |
| P1：每任务持久提交 | 写入/校验 → 数据 sync → ready 元数据 sync → 通知 | 同步调用频率和前台尾延迟 |
| P2：有界组提交 | 收集一组完成写入 → 共同数据屏障 → 对应 ready 屏障 → 通知该组 | 批次等待上限、公平性、失败覆盖范围和崩溃边界 |
| P3：对象发布 | 临时 chunk 写入/校验和同步 → 发布文件 → 同步目录及必要索引 → 宣告持久可用 | rename 的原子可见性不等于掉电持久性；多对象索引需要一致顺序 |

P3 主要与 S2 组合；P1/P2 可适用于不同布局。首轮不用跑所有笛卡尔积：先对照 S1+P1 与 S2+P3，再在通过正确性门槛的路径上对照有界 P2。**批量提交不是必然的后期优化，也不是必选；它可能影响首版布局选择。**

局部完整性是单独门槛：整 blob digest 无法独立验证任意小 Range。可信分块索引必须绑定 blob、offset、length、摘要及版本，且索引本身受信；若当前没有此能力，就明确依赖的传输/存储信任边界，不能让 bitmap 替代校验。

比较布局时使用相同校验要求。不能让 S1 不校验、S2 强校验，再把性能差异全部归因于布局。若只做测试用分块摘要，不能因此宣称生产镜像分发格式已具备它。

## 6. 选型三：共享任务怎样组织

必须满足的是同一授权内容不重复取数、取消不误伤其他等待者、有界执行；以下具体实现都未定：

| 候选 | 组织方式 | 需要验证 |
| --- | --- | --- |
| T1：内容级任务表 | 锁内认领缺失单元，任务持有结果，每个等待者独立订阅 | 部分重叠、竞争窗口、通知丢失、锁范围、取消与重新登记 |
| T2：内容 owner/消息队列 | 一个内容 owner 串行处理状态变更，I/O 在有界 worker 执行 | 热内容瓶颈、队列背压、owner 退出、跨内容公平性 |

不要求为 T2 引入 actor 框架；可用最小消息队列原型。也不能把现有 5ms 轮询当作必须兼容的行为。ready 查询、任务结果和每 VM 映射状态分离是约束，不强制某个 Rust 类型。

Conch 提供操作取消、授权和预算，不逐个管理下载任务；lazyd 管执行和等待关系；StratoVirt 只关联本区域请求/完成。凭据刷新不能替换内容任务 owner，退出一个 VM 不能删除公共任务。

## 7. 选型四：handler 与完成放在哪里

| 候选 | VMM 内的职责 | lazyd 内的职责 | 主要风险 |
| --- | --- | --- | --- |
| H1：内部 handler | 读 UFFD、关联区域、请求范围、完成、关闭 | 内容、任务、缓存、授权与供数 | VMM 数据面代码、并发和阻塞路径扩大 |
| H2：外部 handler | 注册/交接、就绪、校验并执行自身 remap、失败/关闭 | 事件消费与区域适配，再调用内容核心 | 多一层交接/完成关联、共享服务故障域、重连与迟到事件 |
| COPY 对照 | 按实际机制完成私有目标页 | 可复用内容供数 | 多份匿名物理页；只作为可行性和成本基线 |

H2 为主方案方向：lazyd 适配模块消费事件，内容核心供数，VMM 保留映射与运行控制，Conch 管生命周期。选择依据是收敛 VMM 策略与并发职责，并保持供数服务可复用。默认单 lazyd 进程、多会话、有界执行，详见[运行架构](../06-lazyd-design/03-runtime-architecture.md)。

先验证 H2 的上游接入成本、失联后停止能力和交互开销。若出现不可接受的复杂度、时延或恢复问题，再评估 H1，不同时建设两套产品路径。方向选择不等于实验通过，具体协议仍未冻结。

缓存布局实验先固定完成方式；handler 实验固定内容和缓存布局，避免同时改多个变量。StratoVirt 不因此增加 registry、缓存 GC 或统一 RAM/pmem 框架。

## 8. 如何验证：小实验，不先重写三仓

### 所有实验共用的记录

执行前给维护者看架构、参与进程、读写目录、注入点、预算和成功/失败标准。先固定代码 commit、kernel/KVM、宿主机页大小、文件系统/挂载参数、CPU/内存、网络条件和镜像 digest。

测试只使用隔离目录/端口和明确创建的 VM。模拟网络用测试服务的延迟/限速，不修改宿主机全局网络或清全局 page cache；冷缓存用新内容对象/独立缓存目录，并如实记录仍可能存在的 OS 缓存影响。

共同工作负载：连续读、稀疏随机读、跨单元边界、尾页、两 VM 重叠读取、只取消其中一个、活跃映射下 GC。真实应用选择至少一个小工作集和一个较大工作集，内容预先固定。

| 实验 | 回答的问题 | 做什么 | 通过门槛与输出 |
| --- | --- | --- | --- |
| E0：基线与证据审查 | 现有能力和约束是什么 | 固定三仓版本，核对候选涉及的 helper/生命周期；列出可复用测试 | 每条“已有”有版本/代码位置；未知不写成可用 |
| E1：布局与映射 | S1 或 S2 的代价是否可接受 | 相同内容/读轨迹，单进程及两 VMM 映射原型；固定提交/校验承诺 | 字节对拍、只读、共享身份正确；记录 FD/VMA/inode/磁盘/PSS/延迟，不预填胜者 |
| E2：提交与恢复 | P1/P2/P3 会不会错误宣告 ready | 在写入、数据屏障、ready/发布、通知各边界注入错误和进程终止；重开 | 已承诺可持久复用的数据可正确恢复；未承诺范围可重新取数但不能读错 |
| E3：任务与取消 | T1/T2 能否去重且有界 | N 个部分重叠请求，单调用者取消、来源刷新、队列饱和、失败重试 | 重叠单元无重复有效取数，通知不丢；其他等待者正确；连接/队列/字节上限不被突破 |
| E4：handler 与停止 | H2 是否满足主方案门槛 | 固定缓存，真实 KVM fault、FD/范围完成、相邻页、旧代次、handler 退出/stop；必要时对照 H1 | 正确完成访问和写保护；控制面可处理停止；无期限等待/FD 泄漏即不通过 |
| E5：联合业务确认 | 组合后是否有实际价值 | 已选候选接选择性 prepare、guest DAX、共享和失败闭环；与 full 对拍 | 业务可用/首请求/尾延迟、下载放大、资源占用、停止结果均有可复现记录 |

E2 的进程 kill 不模拟真实掉电。掉电保证还需要存储故障模型、屏障顺序审查及专门环境；不得把 reopen 单测写成硬件掉电证明。组提交测试需要说明某个 ACK 对应哪次完成的屏障。

建议先做 E0、E1/E2，再做 E3/E4，最后 E5。逻辑依赖是先明确导出对象和寿命，再冻结完成协议；调度与 handler 的独立静态审查可提前。没有必要等所有快照适配器实现后再选镜像缓存。

### 如何比较性能而不凭印象

同一轮只改变一个主要变量；校验、持久化、网络、工作集、并发和预算保持等价。每种配置重复测量，记录分布与原始样本；少量样本不声称稳定 p99。运行前约定操作 deadline、资源硬上限和可接受退化，而不是看完结果再移动标准。

先以正确性、安全、可结束性作为硬门槛；通过后比较业务可用时间、首次请求、尾延迟、下载字节、写入/sync 开销、PSS 和元数据/FD/VMA 成本。性能接近且没有需求缺口时，优先最少跨仓状态和维护成本的方案，不为换设计而换。

## 9. 三仓如何一起作决定

| 仓库 | 本阶段必须回答 | 本阶段不做 |
| --- | --- | --- |
| Conch | 内容与运行引用在哪个 owner；选择性准备如何真实发布；持久身份如何独立于节点缓存布局；后续快照依赖怎么引用 | 不固定 sparse_path/单 FD 为永久 schema；不接每次缺页热路径 |
| lazyd | 缓存对象、提交、任务、会话与授权的边界；哪种布局和执行模型满足预算 | 不默认保留旧 Instance、bitmap 格式或数据面接口 |
| StratoVirt | 只读区域、FD/范围完成、就绪、停止所需最小能力；候选对代码和回归的真实影响 | 不为候选加完整下载、索引、GC、预取或新恢复引擎 |

联合决定不是三仓同等规模扩张。某个候选把额外复杂度转移给另一仓时，要计入总体成本，不能只展示 lazyd 代码变少。
