# OverlayBD：把快照作为分层块视图

> 阅读后能说明对方解决了什么、哪些经验可用于三仓、选择还需要什么证据。以下借鉴均是建议，不是已冻结接口。

## 对方具体做了什么

逻辑块从最新层查到父层，远端缺失块按需取回。只读历史层上方有可写顶层，commit 或 live snapshot 将变化保存/切换，使新写入进入后续私有状态。

第一方参考：[对应文档或源码](https://github.com/containerd/overlaybd/blob/f63addfd8e51bd9eeecc12f5f4670c281a74d6e8/README.md)。[SRC-OVERLAYBD-001] 核查日期与成熟度沿用[来源清单](../../appendix/source-inventory.md)，不是本次重新运行产品。

完整解释：[读取路径](01-data-path.md)、[缓存与快照生命周期](02-cache-snapshot-lifecycle.md)。

## 对数据服务的具体启发

镜像服务回答“某个 blob 的哪些字节”，分层快照还要先回答“当前逻辑地址由哪一层提供”。我们应把这两步分开：视图解析器处理父层顺序、覆盖和显式零；内容核心只对已经确定的不可变对象范围取数、去重和缓存。两个快照引用同一父层时可以共享字节，却不能共用各自的当前写层状态。

这意味着 lazyd 将来接入快照时，不是给现有 FETCH 加一个 snapshot_id 就完成了，也不必把整个块设备写入引擎搬进来。可以复用专用后端的视图解析，再接共同内容服务。上述 README 支持分层读写与封存能力的判断，但不足以证明我们的共享任务、取消或崩溃回收策略；这些是待设计的边界。

## 三仓怎样共同借鉴

| 项目 | 可考虑的改动 |
| --- | --- |
| Conch | 固定快照谱系、设备布局与一致性点；封存后发布不可变视图，为新的私有写层建立独立使用关系。 |
| StratoVirt | 复用标准块设备与状态保存，协同排空 I/O；不解析镜像 tag、父层索引或远端位置。 |
| lazyd | 将视图解析与内容缓存分开；按确定对象合并读取任务，保留调用者的视图代次与取消状态，不把当前可写层放入共享只读 cache。 |

## 选择与差异

当前只读 rootfs 主线仍是 EROFS + pmem/DAX；这里主要为后续私有写层和历史磁盘快照提供经验。整盘块方案保留为对照，不把 TCMU/NBD 引擎列为镜像懒加载首版任务。

## 如何验证

后续快照阶段验证父层优先级、显式零与继承的区别、封存切换、磁盘与 RAM 一致性、双 VM 写入隔离；两个视图读取相同不可变来源时检查下载去重，取消一个视图不能破坏另一个视图的任务。

参见[数据服务横向比较](../../03-design-comparison/08-data-service-architecture.md)与[磁盘快照比较](../../03-design-comparison/02-writable-upper-and-snapshot.md)。
