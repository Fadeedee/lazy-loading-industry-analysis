# SOCI：索引如何绑定不可变内容

> 阅读后能说明对方解决了什么、哪些经验可用于三仓、选择还需要什么证据。以下借鉴均是建议，不是已冻结接口。

## 对方具体做了什么

zTOC 保存 TAR 文件位置及压缩流检查点状态，让 span 可以独立解压。SOCI 的 v1 外置索引与 v2 构建期转换有区别，不能笼统描述为完全不改镜像。

第一方参考：[对应文档或源码](https://github.com/awslabs/soci-snapshotter/blob/238af848f32fcb887072c144b09ee65a3a895f9c/docs/glossary.md)。[SRC-SOCI-004] [SRC-SOCI-001] 核查日期与成熟度沿用[来源清单](../../appendix/source-inventory.md)，不是本次重新运行产品。

完整解释：[读取路径](01-data-path.md)、[缓存与快照生命周期](02-cache-snapshot-lifecycle.md)。

## 三仓怎样共同借鉴

| 项目 | 可考虑的改动 |
| --- | --- |
| Conch | 选择确定内容与必要的派生索引，分别保护引用/授权；发布 Template 前验证组合，而不是用路径存在表示全部准备完成。 |
| StratoVirt | 通过 source 能力使用数据，不依赖 registry tag 或压缩流细节。 |
| lazyd | 把逻辑范围解析与物理内容取数分层；内容缓存不以当前请求/凭据为身份，索引和数据版本必须匹配；局部校验、下载上限和请求去重分别处理。 |

## 对数据服务的具体启发

索引不是另一个随便缓存的 JSON。它决定读取哪段字节，必须绑定确定内容、大小和布局，并参与授权与引用保护。缓存命中不能绕过这些检查，来源凭据刷新也不应重新创建同内容缓存。

原生 EROFS 主线不需要为了模仿 SOCI 增加 zTOC、TAR 解码或新的镜像格式。借鉴的是“逻辑位置通过可信元数据定位内容”。本节未审计 SOCI 的全部队列、会话取消与 GC 实现，不能从 span 概念推定它们已解决。

## 选择与差异

如果以后接入压缩快照来源，再比较构建索引与在线解码成本；当前不增加这项前置。span 的默认大小也不能直接复制成 lazyd 的缓存、下载和映射统一单位。

## 如何验证

先测内容/索引不匹配、越界、缓存命中授权、凭据刷新和重复 prepare；增加编码适配时再测 span 边界与随机读放大。

对象、任务和权限的联合取舍见[数据服务问题与证据](../../03-design-comparison/08-data-service-architecture.md)。
