# CRIU：恢复任务需要有明确的供页生存期

> 阅读后能说明对方解决了什么、哪些经验可用于三仓、选择还需要什么证据。以下借鉴均是建议，不是已冻结接口。

## 对方具体做了什么

CRIU lazy-pages 与 page server 面向 Linux 进程地址空间，支持把部分页面延迟到访问时供应。需要可用的页来源，供页阶段与恢复后执行阶段可能重叠。

第一方参考：[对应文档或源码](https://github.com/checkpoint-restore/criu/blob/criu-dev/Documentation/criu.txt)。[SRC-CRIU-001] 核查日期与成熟度沿用[来源清单](../../appendix/source-inventory.md)，不是本次重新运行产品。

完整解释：[读取路径](01-data-path.md)、[缓存与快照生命周期](02-cache-snapshot-lifecycle.md)。

## 对数据服务的具体启发

“数据源”不一定是可以永久重开的本地文件，也可能是有生存期的供页服务。我们应让来源接口明确可服务阶段、超时、取消和关闭条件；Conch 只有在本次恢复不再依赖它时才能释放相应资源，不能将恢复 API 返回等同于来源已无用途。

对 lazyd，共同内容缓存应只接确定的不可变字节。若来源是有状态的页服务，适配器必须先明确快照视图和页面版本，不能把运行中可变内存直接按地址当作共享内容。CRIU 的命令文档证明的是 lazy-pages/page server 用法，不足以证明它具备我们需要的跨 VM 去重、凭据隔离或崩溃后缓存 GC。

## 三仓怎样共同借鉴

| 项目 | 可考虑的改动 |
| --- | --- |
| Conch | 记录恢复对来源的使用关系，管理取消、失败与延迟释放；来源丢失时给出明确的沙箱状态。 |
| StratoVirt | 保留 VM RAM 恢复契约和失败通知；区分 host HVA 与 guest 进程地址空间，不把 CRIU 当作 VM backend。 |
| lazyd | 用类型适配器连接确定的只读快照来源或页服务；共享取数不共享各 VM 的页状态，来源关闭与缓存淘汰分别处理。 |

## 选择与差异

借鉴供页生命周期，不复制 CRIU 进程恢复格式。先完成 pmem 镜像服务，再按上游 RAM 恢复能力接来源；既不预设所有来源必须共用同一传输，也不为保持旧实现而拒绝复用合适的内容组件。

## 如何验证

后续验证来源提前退出、断网、VM 取消和后台供页未结束时的清理。错误必须结束等待并保留诊断；一个会话失效不能回收另一个会话仍在使用的不可变数据。

参见[数据服务横向比较](../../03-design-comparison/08-data-service-architecture.md)与[生命周期和安全边界](../../03-design-comparison/07-lifecycle-failure-and-security.md)。
