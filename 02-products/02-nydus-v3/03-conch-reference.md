# Nydus v3：把内容能力与访问入口拆开

> 阅读后能说明对方解决了什么、哪些经验可用于三仓、选择还需要什么证据。以下借鉴均是建议，不是已冻结接口。

## 对方具体做了什么

实验分支围绕原生 EROFS、内容去重与压缩/取数粒度、工作集预取及多种入口组织能力。它提供可研究的方向，不等于所有前端已经成熟或性能可以直接搬用。

第一方参考：[对应文档或源码](https://github.com/dragonflyoss/nydus/blob/9d769780aeb7/README.md)。[SRC-NYDUSV3-001] 核查日期与成熟度沿用[来源清单](../../appendix/source-inventory.md)，不是本次重新运行产品。

完整解释：[读取路径](01-data-path.md)、[缓存与快照生命周期](02-cache-snapshot-lifecycle.md)。

## 三仓怎样共同借鉴

| 项目 | 可考虑的改动 |
| --- | --- |
| Conch | 按实际格式需要发布绑定内容版本的索引/工作集及授权引用；区分转换产物和原始内容，不强迫所有镜像新增索引。 |
| StratoVirt | 消费选定的逻辑布局和 source 能力，不必理解具体压缩存储格式。 |
| lazyd | 把内容标识、源端编码范围、缓存记录单元和请求窗口分开；类型适配解析逻辑位置，内容核心负责任务、校验和存储，不能用现有 unit_bytes 同时固定全部粒度。 |

## 对数据服务的具体启发

这个实验最有价值的问题是：**去重、解码、校验、下载和映射是否必须用同一个大小？** 对 lazyd，调大下载窗口不应修改已有 bitmap 格式；将来换压缩来源也不应让 VMM 理解压缩块。

本节依据是实验分支说明，不是对其全部调度和缓存代码的审计。它不证明多入口取消、持久化和回收已完善，也不要求我们实现所有入口。首版先用原生 EROFS 验证上述粒度边界。

## 选择与差异

内容核心可以重构，现有 API 和结构只是待评估的实现，不是设计约束；同时不为未来能力提前制造通用插件框架。fanotify 不作为当前 guest pmem/DAX 入口。

## 如何验证

先测 EROFS 边界、不同请求窗口下的缓存兼容、任务去重和实际下载放大；只有新增编码来源时才要求解码跨度、索引绑定和格式升级测试，不把它们全部列为首版任务。

与其他来源共同推导的结论见[数据服务问题与证据](../../03-design-comparison/08-data-service-architecture.md)。
