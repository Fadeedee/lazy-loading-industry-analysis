# QEMU：前台缺页和后台恢复怎样协调

> 阅读后能说明对方解决了什么、哪些经验可用于三仓、选择还需要什么证据。以下借鉴均是建议，不是已冻结接口。

## 对方具体做了什么

Fast Snapshot Load 按 mapped-ram 布局读取本地快照，fault thread 与 eager thread 使用页面状态协调领取。后台线程不只是预测，它还负责让恢复最终结束，避免未访问冷页令迁移状态长期悬挂。

## 对数据服务的具体启发

QEMU 的页面领取状态解决前台与后台“谁安装这一页”的竞争。我们还需要另一层独立状态，解决多个消费者“谁下载这一段内容”的竞争。前者属于某次 VM 恢复，后者属于确定的不可变内容；不能把两种 bitmap 或任务表合为一张。

因此 lazyd 的共享任务可以让两个 VM 只下载一次快照字节，但每个 VM 仍需各自确认页面尚待恢复。后台任务晚到时，不能用旧快照覆盖 guest 已写入的页。镜像预取还应允许取消或长期不下载冷数据，这与 QEMU 示例中最终完成恢复的 eager thread 目标不同；网络自适应和跨会话公平队列是我们的设计要求，不是该文档已经实现的结论。

## 三仓怎样共同借鉴

| 项目 | 可考虑的改动 |
| --- | --- |
| Conch | 区分可运行与恢复完成；选择是否后台物化以及来源保留期，为需求取数与后台任务分配预算。 |
| StratoVirt | 复用上游页状态与恢复规则，防止重复填页覆盖新写入；与所选 handler 明确完成和停止边界，不另造通用框架。 |
| lazyd | 维护内容级任务与每会话等待关系；前台命中后台任务时复用并提升优先级，取消一个消费者不等于清除公共内容 ready。 |

## 选择与差异

本地快照调度可借鉴，不宣称它已实现远端网络自适应。是否全量后台物化由产品目标决定，不能统一套到长期按需镜像。

## 如何验证

后续 RAM 阶段验证从不访问的最后一个冷页如何影响完成状态，前台/后台同时请求同页是否只安装一次，业务新写入是否保留。两个 VM 共用缓存时各自恢复状态必须独立；取消后台预取不能中断仍有前台等待者的共享下载。
