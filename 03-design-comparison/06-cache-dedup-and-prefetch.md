# 网络慢时，怎样让业务更快可用？

> 多拉数据不一定更快。把内容缓存、预测下载和提前映射分开，才能判断各自有没有收益。

## 五个动作

| 动作 | 解决什么 | 不意味着什么 |
| --- | --- | --- |
| 持久内容缓存 | 下次少下载 | VM 已有映射 |
| inflight 去重 | 并发请求不重复取数 | 所有等待者都已成功 |
| 工作集/预测预取 | 访问前取回可能需要的内容 | 取回的数据一定被用到 |
| prefault/提前映射 | 减少第一次地址访问的处理 | 必须从远端下载新内容 |
| 后台物化 | 让恢复逐步完成 | 一定只是可随时取消的预测任务 |

[eStargz](../02-products/03-stargz/01-data-path.md)的 prioritized files、[Nydus](../02-products/01-nydus-v2/01-data-path.md)的 prefetch/prefault、[QEMU](../02-products/09-qemu/01-data-path.md)的后台恢复处于不同层次，不是同一个算法。

## 三仓提供不同信息

**Conch** 知道这是冷启动还是恢复、用户 deadline、Template 工作集、节点并发与预算。

**StratoVirt/handler** 可观测缺页事件、等待或已完成区域，但不等于掌握文件级工作集和全部内存访问。先利用已有事件和指标；新增反馈需证明收益并权衡成本与隐私，不要求 VMM 建立新的访问追踪框架。

**lazyd/数据服务** 知道缓存、远端请求、鉴权、排队和传输成本，负责有界调度和去重。

因此可以增加经过验证的最小访问反馈、优先级或预算协商，而不是把所有判断固定在某个现有请求格式里。网络策略和预取算法留在数据服务侧，遵守 [StratoVirt 首版边界](../04-conch-design-reference/05-stratovirt-responsibilities.md)。

## 先测纯按需，再独立加入优化

纯按需也需要可靠的任务基础：内容级共享任务、可取消等待、有界 socket/磁盘执行，以及提交后才发布 ready。它们不是预取功能的附属补丁；先在[lazyd 架构](../04-conch-design-reference/04-lazyd-responsibilities.md)中解决，来源依据见[数据服务比较](08-data-service-architecture.md)。

1. 纯按需为基线，记录网络/鉴权、排队、传输、校验和页完成时间。
2. 加可关闭、有上限的顺序预取，验证实际利用率。
3. 加 Template 历史工作集预取，明确绑定的镜像/快照版本。
4. 单独测试提前映射本地 ready 范围，记录额外启动等待。
5. 有稳定样本后再加延迟/吞吐反馈，而不是凭第一次慢请求扩大下载。

| 观察 | 可以尝试 | 必须限制 |
| --- | --- | --- |
| 连续读取、请求固定开销高、吞吐足够 | 扩大预测窗口、合并相邻范围 | 最大窗口、带宽、下载放大 |
| 随机读取或预测命中低 | 收缩预测，恢复按需 | 避免窗口频繁振荡 |
| 前台排队、超时或拥塞 | 暂停/缩小后台任务 | 为前台预留容量 |
| 首次鉴权/冷连接慢 | 继续采样、复用连接 | 不把首字节耗时直接等同 RTT |

这是本项目建议，不声称参考项目已实现同一套反馈算法。

## 远端聚合启动工作集

**后续可选优化，尚未实现或验证，不是首版启动依赖。** 将多个可比实例在启动阶段需要的范围聚合成工作集清单，供后续实例参考。远端学习“哪些范围经常先用”，本地仍决定“现在值得预取多少”。

例如，同一版本 Python Template 的多个实例反复需要解释器和部分库，可以优先准备这些范围，而不是预取所有用户偶尔用过的数据。先面向只读镜像验证；私有磁盘和内存快照不自动加入跨用户统计。

### 从采集到本地执行

1. **标记窗口：** Conch 记录内容版本、平台、工作负载类别及启动阶段。应用就绪或首个业务请求作为可选结束点，超时/失败和未完成样本单独标记。
2. **采集需求：** lazyd/数据适配器记录实际需求触发的逻辑范围、首次触发时机与等待；区分 demand、预取、放大下载及缓存命中。使用内容/视图相对偏移，不把某台 VM 的 HVA 当作跨实例身份。
3. **异步上报：** 本地先去重和汇总，以有界队列上传。采集可关闭；上报失败、队列满或统计服务不可用，不影响缺页供数和启动。
4. **远端聚合：** 在相同分组和可比采样条件下，按独立启动次数计算范围需求比例，而非累加某个实例的重复读取。结合首次需求时间、字节成本、样本量和新鲜度排序。
5. **发布清单：** 生成带版本、内容绑定、范围坐标/粒度、优先级、样本信息与有效期的建议清单。可由 Conch 控制面后台任务生成并存储，不要求 OCI Registry 做统计，也不预设新增独立服务。
6. **本地执行：** Conch 选择适用清单和预算，lazyd 校验后跳过已缓存范围，结合当前需求、网络、队列和缓存容量执行有界预取。合并相邻请求也受下载放大限制，不能把离散热点拼成任意大的连续范围。
7. **效果反馈：** 记录应用可用时间、首请求、下载量及可观测的预取利用情况，供下一版调整；保留无预取对照，不把本次清单永远当作真值。

清单可以随 prepare 元数据取得或在后台更新，并使用本地有效副本。没有清单、过期、版本不匹配或服务不可用时，回到普通按需策略；不得为了等待新统计阻塞创建。是否等待一小部分高优先级预取另由 Conch 显式决定，并计入启动耗时。

### 身份与统计不能混淆

| 信息 | 要解决的问题 |
| --- | --- |
| 内容 digest / 不可变快照视图与布局版本 | 范围到底属于哪份数据；不能只绑定可变 tag |
| 平台、工作负载类别、启动或恢复阶段 | 不把不同程序、架构和运行阶段混成一个热点集合 |
| 采样窗口、是否启用预取、映射/取数粒度、冷/热条件 | 不把不同观测条件下的频次直接比较 |
| 样本数、需求比例、首次需求时间、新鲜度 | 判断置信程度及执行顺序，不固定算法或阈值 |
| 清单版本、范围、优先级、有效期 | 让消费者校验、限额、失效和回退；不是冻结的 API schema |

这些是**工作集统计身份**，不改变内容缓存身份。同一内容被不同工作负载使用，仍可在授权范围内复用缓存，不因统计分组重复存储。工作负载类别使用受控标签，不直接上传启动命令、环境变量或凭据。

### 避免越预取越热门

下载了一个大范围，不代表 guest 用了其中每一页；预取请求也不能增加真实需求计数。内容已经映射后，后续访问通常不再产生相同的 UFFD missing 事件，提前映射或放大 remap 还会遮住一部分首次访问。因此缺页日志只能表示所选机制下的需求触发样本，不能直接宣称是完整工作集。

同一次启动对同一统计单元只计一次，单元粒度与采样方式一起版本化。保留纯按需的受控对照，并记录映射粒度；没有观测到需求不能简单等同于“没有使用”。预取利用率要交代测量方式，不能仅以“预取后没有缺页”证明命中，也不为补全统计而默认新增 VMM 全量访问追踪。

### 三仓与安全边界

| 部分 | 职责 |
| --- | --- |
| Conch | 定义阶段和工作负载分组，组织授权、聚合/发布、清单选择和启动预算 |
| lazyd / 数据适配器 | 采集并汇总需求范围、异步上报、校验清单、去重和执行预取 |
| StratoVirt | 保持必要的缺页、映射与错误处理；不增加远端统计、热点学习或预取算法 |

跨用户聚合默认关闭；公共只读内容也需明确授权和汇总策略，内容公开不意味着访问模式可以任意公开。租户私有内容和快照默认隔离，最小化上传信息并限制保留期、查询权限和单个上报者的贡献，避免泄漏或恶意样本操纵热点。

清单只是性能提示，不授予数据访问权限，也不是内容完整性证据。发布与读取需要可信来源和授权；lazyd 仍校验目标内容绑定、范围边界、清单大小和预取总量，沿用内容校验与持久化顺序。不可信或畸形清单应被拒绝并回退按需，不能据其指令扩大可访问内容集合。

### 借鉴什么以及怎样验证

[eStargz 的工作负载优化](https://github.com/containerd/stargz-snapshotter/blob/c2bf18e5a94dcfd959cabf744f4bbb4ef8d980a2/docs/estargz.md#example-use-case-of-prioritized-files-workload-based-image-optimization-in-stargz-snapshotter)在转换时运行指定工作负载，记录访问文件并按访问顺序放到优先区域；运行前预取 landmark 之前的区域。[SRC-STARGZ-002]

借鉴的是“从实际工作负载得到预取集合”。本建议增加跨实例异步聚合及独立清单，不要求改写 EROFS 布局或重新构建镜像；该来源不能证明跨用户在线聚合已由对方实现。产品细节见 [eStargz 分析](../02-products/03-stargz/01-data-path.md)。

验证单独分组：纯按需、静态工作集、远端学习清单；先固定在线窗口/提前映射策略，避免混淆收益。用未参与学习的后续启动样本比较启动与首请求延迟、下载放大、带宽/缓存占用、采集成本和适用样本覆盖率。

覆盖新版本/无样本、工作负载变化、冷/热缓存、低带宽、高 RTT、多租户并发，以及统计服务断开、清单过期/越界/伪造、恶意重复上报。只有收益可复现且失败回退不影响普通按需路径，才讨论默认开启。执行顺序见[阶段 4](../04-conch-design-reference/07-phased-roadmap.md#阶段-4性能策略和规模)。

## 正确性不随预取策略改变

已发出的远端请求可能不可抢占，队列优先级不能保证前台完全不受影响。后台需要限制请求大小和并发。前台命中在途预取时复用任务并提升优先级，失败不能标记 ready。

若选固定单位 bitmap，单位属于持久格式，动态调整的是预测窗口；也可以选择其他缓存格式再定义其粒度。物理 fault page、网络请求、校验单位和映射单位不得混为一谈。

准备阶段是否等待工作集，是 Conch 可观察的策略；运行阶段当前需求满足后不必等待无关预测范围。内存后台物化还要遵守页代次，防止覆盖恢复后的写入。

## 验收

full、纯按需、预取、提前映射分组对照。覆盖小/大镜像、单/多 VM、冷/热 cache、顺序/随机访问、高延迟/限带宽/抖动网络。

记录业务可用时间、首次请求、fault p50/p99、实际远端字节、下载放大、预取利用率、排队和 PSS。预取利用率要有固定观测窗口；网络模拟仅在隔离代理或 network namespace 里进行。

没有实测前，保持策略可关闭，不预设自动切换默认阈值。
